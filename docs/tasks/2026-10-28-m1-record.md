- H1、M1 與 M4 由主對話自行重現。修正的方式如下：
  - 改成兩份 clone。
  - 所有 git 呼叫都使用強化的環境：`GIT_CONFIG_GLOBAL=/dev/null`、`GIT_CONFIG_NOSYSTEM`、`GIT_NO_REPLACE_OBJECTS`、`XDG_CONFIG_HOME=/nonexistent`，並將 hooksPath 指向 `/dev/null`、關掉 fsmonitor。
  - 在 clone 內重做 lineage 檢查。
  - 報表的決策一致性與路徑集合都要比對。
  - lint 界線改用兩條不同的 rule，避免互相覆蓋。
  - 清理失敗不會蓋掉結果，新增 `REVIEW_INTERNAL_ERROR`。
- 一併修正：L1（`show` 顯示最新事件與 stale）、L2（控制字元跳脫）、L3（dirty 快照失敗時 fail-closed）、L5（`resultTree` 失敗不再讓 Attempt 變成 INCONCLUSIVE，這是一個 regression）、L6（timeout 時 `rm -f` 孤兒 container）、改用 `--mount`，以及 L7 的突變補測。
- 突變實驗：47 個裡只剩 2 個等價突變存活。第三輪又加測一個「只覆寫 `core.excludesFile`」的突變，回歸測試能殺掉它。
- 刻意取捨（D-42）：argv 不加 `--security-opt no-new-privileges`。本機 snap 版 Docker 29.8.0 加了它，image 的 entrypoint 就無法 exec（主對話已重現）；`--cap-drop ALL` 加非 root 的 `--user` 仍讓 container 內的 setuid 程式拿不到 capability。

## 五、限制與後續

- 已知限制（Harness `docs/usage.md`「審查交接」一節）：
  - 不支援 submodule、LFS 與 SHA-256 的 repo。
  - 不採用使用者的全域 git 設定，可能造成 fail-closed 的 `CANDIDATE_TREE_MISMATCH`。
  - 乾淨副本只有 commit 進去的內容。
  - 未選入的檔案只代表機械審查未選入（DEV-01）。
  - state dir 不可放在 snap Docker 看不到的 `/tmp`。
- 第三輪審查列出、仍為低風險的項目：
  - `import()`／`createRequire` 能繞過 lint（既有問題）。
  - 預設的 `git diff --check` 在乾淨副本上永遠通過。
  - timeout 且 `rm -f` 也失敗時，`chmodSync` 有理論上的 symlink 競態。
  - bidi 字元沒有跳脫。
  - `GIT_CONFIG_NOSYSTEM` 沒有專屬測試。
  - 端到端腳本的 `expect_lacks` 在檔案不存在時會直接通過。
  - 既有設計：check 對使用者 `.git` 有寫入權，能影響同一 workspace 下一個 Attempt 的 path policy。
- 未驗證：
  - 真實 Docker 下的 timeout `docker kill`。
  - 以 root 實際執行時的拒絕。
  - rootless／userns-remap 的 Docker。
  - shellcheck（本機沒有安裝）。
